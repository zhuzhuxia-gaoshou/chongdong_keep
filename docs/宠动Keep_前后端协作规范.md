## 二、五条铁律

1. **契约先行**：先改契约，再写代码。没有写入契约的接口不算数，对方没有义务适配。
2. **密钥纪律**：一切密钥（和风天气、腾讯地图、短信、OSS/COS、JWT 私钥、数据库密码）**不进 Git、不进任何 md/PDF 文档、不发群里**。只在私聊或密码管理工具中传递。目前 `宠动Keep_项目交接文档.md` 第 4.1 / 11.3 节含真实密钥，该文件**禁止发送给任何外部人员、禁止入库**。
3. **向后兼容**：正式跑通的 `/api/v1/*` 接口不允许悄悄变更。要改，走第三节的变更流程。
4. **阻塞即上报**：任何一方被对方阻塞超过 **1 个工作日**（如等接口、等信息），必须当天明确提出，不得沉默等待。
5. **机器相关配置不入库**：`local.properties`、gradle.properties 中本机路径、各环境 IP/端口清单，提交前自查。

## 三、《API 接口契约》管理制度

- **唯一载体**: 使用 Apifox（或 Postman）建立共享项目，目录按模块分组；同时导出一份 markdown 快照存放在项目根目录（如 `docs/api_contract_v1.x.md`），作为离线兜底。
- **接口生命周期**: 草稿（draft）→ 双方确认（confirmed）→ 已实现（前端已对接 / 后端已上线分开标记）。
- **变更流程**（4 步，缺一不可）:
  1. 提出方在 Apifox 中修改字段/新增接口，并在注释里写明**原因和影响面**；
  2. 通知对方确认（当天响应同意与否）；
  3. 确认后更新快照文件的版本号（如 v1.1 → v1.2）和文末变更记录；
  4. 之后才允许改代码。**未走流程的代码变更，对接时发现按原契约为准回退。**
- **时间戳问题**：每次变更记入变更记录（日期、内容、提出人），避免"你什么时候说的？"式扯皮。

## 四、接口技术规范（保证能对上的硬性标准）

### 4.1 BaseURL 与环境

```
开发:   http://<后端提供的内网或公网IP>:8080        ← 联调用
测试:   https://api-test.chongdong.example.com      ← 上线前回归
生产:   https://api.chongdong.example.com           ← 正式包专用
```

- 后端在每个环境都提供 `/api/v1/ping` 健康检查接口（无需鉴权，返回 `{code:0, data:{service:"chongdong-api", time:"..."}}`），前端用它做连通性诊断。
- 前端通过编译期注入切换环境，**源码中不出现任何环境地址明文之外的可切换魔法**：

```bash
flutter run \
  --dart-define=API_BASE_URL=http://x.x.x.x:8080 \
  --dart-define=QWEATHER_KEY=... --dart-define=QWEATHER_HOST=... --dart-define=TENCENT_MAP_KEY=...
```

### 4.2 统一响应结构

所有业务接口一律返回如下包裹结构：

```jsonc
{
  "code": 0,            // 0 = 成功；非 0 见 4.6 错误码
  "message": "ok",      // 给开发者看的错误描述；用户可见文案由前端自己做映射
  "data": { }           // 业务数据，出错时可省略
}
```

HTTP 状态码保留其网络语义（401 未带 token、429 限流、500 服务器异常），用于网关/框架层；**业务成败只看 body.code**。前端 HTTP 库统一在拦截器里解包，业务代码永远只处理 `data` 与 `code`。

### 4.3 认证方案

- 采用 **JWT Bearer Token**：请求头 `Authorization: Bearer <accessToken>`。
- 登录流程（替换现在的壳子登录）：

```
POST /api/v1/auth/sms-code   { phone }                  → 发送验证码（60s 限流）
POST /api/v1/auth/login      { phone, smsCode }         → { accessToken, refreshToken, expiresIn }
POST /api/v1/auth/refresh    { refreshToken }           → 新 accessToken
```

- accessToken 有效期 ≤ 7 天，refreshToken ≤ 30 天；401 时前端自动 refresh 并重放一次，失败则引导重新登录。
- 所有非 auth 接口默认需要鉴权；公开接口（ping、公告类）在契约中显式标注「免鉴权」。

### 4.4 字段命名与类型

| 规则 | 规定 |
|---|---|
| 字段命名 | 小驼峰 camelCase（与现有 Dart 模型一致，后端序列化时转换） |
| ID 类型 | 一律**字符串**（禁用自增数字直出，防 JS/Dart 大数精度与猜测遍历）；服务端生成 |
| 时间类型 | ISO 8601 字符串，**必须携带时区**，如 `2026-08-27T14:30:00+08:00`；后端存库格式自定，出网必带时区 |
| 枚举类型 | 出网一律用**稳定字符串**，不用数字下标；映射关系固定如下 ↓ |

| 含义 | API 值 | 现 Dart 枚举 index |
|---|---|---|
| 物种 | `"dog"` / `"cat"` | PetSpecies 0 / 1 |
| 性别 | `"male"` / `"female"` | PetGender 0 / 1 |
| 运动类型 | `"walkDog"` / `"catPlay"` | ExerciseType 0 / 1 |

> 前端在做本地存储 → API 切换时，加一层 DTO 适配器做 index ↔ 字符串转换，Dart 模型本身不动。

### 4.5 GPS 轨迹数据

- 单个轨迹点结构与现有 `GeoPoint` 完全一致：

```jsonc
{ "latitude": 31.2304, "longitude": 121.4737, "timestamp": "...", "accuracy": 8.5 }
```

- **坐标系必须在每个坐标字段上标注**。默认约定：客户端上报与服务器存储统一为 **WGS-84（GPS 原始）**；腾讯地图展示为 GCJ-02，转换由显示方负责。⚠️ 当前 MVP 是直接把 GPS 点喂给腾讯地图 WebView 的，国内理论上存在数百米偏移——**联调第一周双方一起实机验证此问题**，若确认偏差则在前端统一加 WGS84→GCJ02 转换后再上报。
- 轨迹上传压缩策略：每 N 米或 M 秒取一点（具体阈值契约定），漂移过滤沿用现有 15m/s 规则在上报前执行。

### 4.6 错误码分段

| 区间 | 归属 | 示例 |
|---|---|---|
| `0` | 成功 | — |
| `400xx` | 参数/校验类 | 40001 缺少必填参数 |
| `401xx` | 认证类 | 40101 accessToken 过期、40102 验证码错误、40103 验证码频繁 |
| `403xx` | 权限类 | 40301 无权操作他人宠物 |
| `404xx` | 资源不存在 | 40401 宠物不存在 |
| `429xx` | 限流 | 42901 短信发送过频 |
| `500xx` | 服务端异常 | 50000 内部错误 |

新错误码只能落在对应区段；新增业务错误码写入契约并由另一方知悉后方可使用。

### 4.7 分页规范

```
请求: ?page=1&pageSize=20        // page 从 1 开始；pageSize 默认 20，最大 100
响应 data: { "list": [...], "total": 137, "page": 1, "pageSize": 20 }
```

### 4.8 文件上传

- 过渡方案：`POST /api/v1/upload`（multipart，返回 `{url}`），后端中转到对象存储，前端不接触对象存储密钥。
- 目标方案（后端评估后可选）：后端签发临时上传凭证，APP 直传 COS/OSS，减少大图流量经过 API 服务器。
- 无论哪种，最终落库与对外暴露的都是 **HTTPS URL**；契约中每种图片资源（头像 / 出发照片）注明建议尺寸与大小上限（头像 ≤ 2MB，出发照片压缩后 ≤ 1MB）。

### 4.9 第三方能力归边（生产化方向）

二期起，天气（和风）与地图逆地理/静态图改为**后端代理转发**：APP 只持有自家用户 token 与 API_BASE_URL，不再持有任何第三方密钥。这样密钥泄露面最小、便于后端统计调用量计费、也能做多用户限流。过渡期内前端直连不受影响。

## 七、Git 协作规范

- **仓库划分**：同一 Git 平台（GitHub/Gitee 任一，均设**私有**）下两个仓库：
  - `chongdong_keep` —— Flutter 前端（现有仓库迁移过去）
  - `chongdong_server` —— 后端 + 部署脚本 + 管理后台
- 两仓库 `.gitignore` 必须包含：`.env`、`*.keystore`、`*.jks`、`key.properties`、`/build`、本机路径文件；以及一切含密钥的 md。
- **分支模型**：`main`（随时可运行）← `dev`（联调集成分支）← `feature/xxx`。合并一律走 Pull Request，本人以外的 merge 需另一个人口头/文字 ack。
- **Commit 格式**：`type(scope): 中文一句话`，type ∈ feat / fix / refactor / docs / chore / test。例：`feat(auth): 对接短信登录接口`。
- **禁止**：force push 到 main/dev；把 apk/node_modules/构建产物提交进库。
- 主 `README.md` 各自维护「如何跑起来」三行命令，确保对方拿到代码 30 分钟内可运行（跑不通算文档 bug）。

## 八、联调流程与质量门槛

### 8.1 后端每交付一个接口，最低验收标准

1. Apifox 契约状态更新为「已实现」；
2. 测试环境已部署且 `/api/v1/ping` 可达；
3. 附一段真实 curl（或 Apifox 运行截图）证明自测通过；
4. 若变更了已有接口，附变更记录链接。

### 8.2 前端对接姿势

- 前端网络层做 **Mock/Live 双模式开关**（契约确定后即按契约造假数据先行开发页面逻辑），Live 模式基于 `API_BASE_URL`。
- App 内开发构建预留环境显示（设置页展示当前 BASE_URL host），避免测了半天不知道连的是哪套环境。

### 8.3 冒烟清单（每轮联调必过）

登录发码收码 → 编辑资料传头像 → 添加宠物 → 上报一次运动记录（含轨迹）→ 打卡日历正确亮灯 → 周报数据与服务端一致 → 排行榜排序正确 → 断网场景有兜底提示。

### 8.4 前端自身门槛

`dart analyze` 零 error 才能合入 dev；任何密钥类改动必须保持 `--dart-define` 注入方式。

## 九、发布与兼容性红线

**前端（不可违反，否则用户无法升级安装）**
1. Android 包名 `com.chongdong.chongdong_keep` 永不改；
2. keystore 签名永久保管（多地备份），丢失 = 全量用户重装；
3. AndroidManifest 权限只增不删；
4. `versionCode` 单调递增，`versionName` 用 `主.次.修订`。

**后端（不可违反，否则线上 APP 直接崩）**
1. 已发布接口不做不兼容变更：不删字段、不改字段类型与语义、不加必填入参；
2. 废弃字段/接口：契约标记 `deprecated`，**至少保留一个大版本周期**后再下线，并在响应 message/头中提前告警；
3. 数据库变更必须用迁移脚本进仓库（可追溯、可回滚），禁止登 production 手改数据/表;
4. 大版本升级考虑 path 版本共存（`/api/v1` → `/api/v2` 并行灰度）。
