## 0. 问题定义

遛狗场景天然存在「停下来」：等红绿灯、偶遇狗友、买水、处理粪便。没有暂停时，这些时间全部计入运动时长——时长虚高，且直接冲击两条**禁改契约**的下游：

| 契约（SPEC §2.3，禁改） | 与时长语义的关系 |
|---|---|
| 打卡判定 `isCompleted && duration≥300s` | duration 取值口径决定 5 分钟门槛的真实含金量 |
| 幂等键 `clientRecordId` | 决定一次遛狗是「一条记录」还是「多条记录」 |
| 运动量公式（推荐分钟数） | 用户看到「已完成 x%」的分母是目标分钟，分子来自 duration 累计 |

因此：**时长语义是产品决策，但它的实现必须在不触碰上述三条契约文本的前提下完成**。下文三种口径都以此为准绳评估。

---

## 1. 三种口径

### 口径 A：暂停计入当日时长（墙钟口径）

`duration = endTime − startTime`（现状语义），暂停只是 UI 上的一个按钮，不改变计时。

- **利**
  - 实现最薄：只加 UI 状态位，计时代码零改动；`WalkSession.elapsedSeconds` 现有「按墙钟回推」的恢复逻辑原样可用。
  - 前后端零契约感知：duration 与起止差恒等，⑭ 的「duration 与起止差偏差 >30% 审计标记」永远不会触发。
- **弊**
  - 时长失真：3 分钟快走 + 20 分钟聊天 = 23 分钟「运动」，目标进度与周报全部注水。
  - **实质架空打卡门槛**：`≥300s` 本意是「真的动了 5 分钟」；墙钟口径下暂停凑秒即可过线——公式没改，但口径的公信力被打穿，等同于变相私改打卡口径（红线意识：这是结果性违规，比改公式更隐蔽）。
  - 反作弊口径被掩护：速度 = 路程 ÷ 墙钟时长，暂停越久速度越低，作弊数据反而更难触发「>60km/h 剔除」。

### 口径 B：暂停不计入（纯运动时长口径）★ 推荐

`duration = Σ 各段纯运动秒数`；暂停期间计时冻结、定位轨迹断点、距离步数停算；继续后从冻结值续计。

- **利**
  - 时长诚实：5 分钟门槛重新等于「真的动了 5 分钟」，打卡含金量与契约本意对齐。
  - **三条禁改契约全部原样成立**（详见 §2 影响面），唯一新现象是 duration 与起止差出现合理偏差，而 ⑭ 明文「采信客户端」，偏差只打审计标记——这是契约预留的合法空间。
  - 反作弊口径反而更准：速度 = 路程 ÷ 纯运动时长，掺假更难藏。
  - 产品面一致：周报/今日目标/排行榜的分钟数都是「运动分钟」，用户心智无需解释。
- **弊**
  - `WalkSession` 恢复逻辑要改：现状「跨进程死亡按墙钟回推」在暂停态死亡时会把暂停时间算回去——需在暂停边界持久化已累计秒数，恢复时优先读存储值（§3 实现要点）。
  - 轨迹出现断点：route 两段之间直线不连续，地图渲染与抽稀逻辑要容忍 gap（catPlay 本就 route=[] 合法，先例存在）。

### 口径 C：分段计（一次会话 = N 条记录）

每次暂停把会话切成一段，恢复即结算上一段、开新段，最终 N 条记录各自上报。

- **利**
  - 每段 duration 都是纯运动时长，与口径 B 同等诚实。
  - 单段数据更「干净」（无超长会话），对「单次 duration>6h 剔除」的反作弊口径更友好。
- **弊**
  - **幂等键面扩大**：一次遛狗产生 N 个 `clientRecordId`，弱网下「部分段成功、部分段进退避重试」的状态组合爆炸，会话恢复/重试队列（AppState._pendingUploads）复杂度显著上升。
  - 记录列表/时间线被碎片化：「一次遛狗」显示成 3 条，与产品心智冲突；周报条数、记录删除（按条）等交互全被波及。
  - 服务端打卡判定不受影响（任一条 ≥300s 即打卡），但用户「凑段打卡」的心智比凑秒更怪。
  - 相比 B 无任何额外收益——B 用一条记录就能达到同样的时长诚实性。

## 2. 推荐口径：B（暂停不计入）——对禁改项的影响面（显式声明）

> 结论先行：**打卡判定口径、幂等键、运动量公式三处契约文本零改动**；时长语义的修正恰好让既有口径回到设计本意。

| 禁改项（SPEC §2.3） | 影响 | 显式声明 |
|---|---|---|
| 打卡判定 `isCompleted && duration≥300s` | **不变** | 公式逐字不动；变化的只是 duration 的取值口径（纯运动时长）——它让「≥300s」恢复「真实运动 5 分钟」的本意，是**修正取值、不是修改口径**。前端本地兜底算法（`getMonthlyCheckIns` 的 `countsAsCheckIn` 规则）与服务端判定三处一致的关系不破坏。 |
| 幂等键 `clientRecordId` | **不变** | 暂停/继续是**一次会话内部状态**，结束仍产出**一条记录、一个 UUID v4 键**。不新增记录、不拆分上报；重复提交 → `duplicated:true` 的幂等语义不变；退避重试队列按会话粒度工作的现状不变。 |
| 运动量公式（推荐分钟数） | **不变** | 公式输入（年龄/品种）与输出（目标分钟）不动；分子（今日已运动分钟）来自 duration 累计，随口径 B 更诚实，进度条语义更可信。 |
| ⑭ 上报校验 | **兼容** | `endTime > startTime` 恒成立（暂停期间会话未结束）；「duration 与起止差偏差 >30%」在长时间暂停的会话里**会触发审计标记**——这是契约明文的「采信客户端」路径，属预期行为，非违规。建议实现时在提交说明中引用本节备查。 |
| 反作弊口径（单次 >6h / >60km/h） | **变好** | 纯运动时长下速度计算更真实，无掩护效应；6h 过滤对纯运动时长更少误伤。 |

**不做的事**：不改 SPEC §2.3/§4.6/⑭ 任何一行；不改服务端；不改 `countsAsCheckIn` 判定；不给打卡门槛引入「暂停豁免」之类的衍生规则。

## 3. 实现要点备忘（拍板后执行，本文不实现）

1. **WalkSession 双字段**：`elapsedSeconds`（已累计纯运动秒数）+ `pausedAt?`（暂停边界时刻）。暂停即持久化；恢复/进程死亡重启时——
   - 若 `pausedAt != null`：直接用存储的 `elapsedSeconds`，**不做墙钟回推**（否则暂停时间被算回）；
   - 若为 null（运动中死亡）：维持现状墙钟回推。
2. **定位与计距同步冻结**：暂停期间不写 route 点、不累计 distance/steps；轨迹 gap 交给渲染层容忍（catPlay route=[] 合法为先例）。
3. **UI 状态机**：`walking ⇄ paused`（结束仅允许从两态发起）；暂停中「结束并结算」按钮文案与确认弹窗按既有温柔文案标尺（§8.1）润色，文案进 BrandCopy 新池（如 `walkPausedPool`），人读镜像同步 `docs/copy_library.md`。
4. **测试**：暂停边界持久化 / 暂停态进程死亡恢复 / duration=Σ分段 三条单测先行；打卡口径回归沿用既有 `mock_records_test` 族。
5. **决策记录**：拍板后在 `docs/PROGRESS.md` §五追加一行（口径 B + 「契约零改动」声明），再动代码。

## 4. 一句话结论

**暂停不计入（口径 B）**：时长诚实、打卡门槛不失真、三条禁改契约逐字不动，代价只是暂停态恢复逻辑的一处小改——这是唯一既满足产品直觉又不碰红线的口径。
