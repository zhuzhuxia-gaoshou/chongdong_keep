| 已有设施 | 位置 | 与本提案的关系 |

## 1. 统一消息模型（两形态共用）

二期好友互动/推送接入时消息流要能平滑混入远程消息，因此本地消息**从第一天就按带 `type` 的统一 DTO 设计**（存储于 `StorageService` 新 key `local_messages`，StringList 存 JSON，上限 50 条 FIFO 淘汰；未读态存 `readAt` 时间戳）：

```
LocalMessage {
  id            // UUID v4（与 clientRecordId 同代策略，仅本地生命周期）
  type          // milestone（里程碑）| reminder（提醒）——二期扩 friend/push
  createdAt     // 生成时间（带时区 ISO8601，与记录 startTime 同规范）
  copyKey       // 文案定位：BrandCopy 池名/键（如 streakMilestones[7]）
  copyParams    // 占位符参数（如 {"days":7}）——存储键而非字面量，
                //   文案永远以 BrandCopy 为唯一出口，人读镜像可随版本更新
  payload       // 点击去向：路由目标（如 '/calendar'、运动入口）
  readAt?       // null = 未读（驱动 Tab 红点）
}
```

红点与未读数进 `AppState`（`unreadMessageCount`），Tab 角标逻辑与 main_page 既有选中态语言一致。

## 2. 形态一：本地提醒历史

**定义**：把「每日运动提醒」的调度/触达痕迹变成消息流条目——今天提醒已设、某个时刻提醒触发过、通知权限被拒导致提醒发不出等。

**信息结构实例**
```
{ type: reminder, copyKey: reminderFired, payload: 去运动入口,
  createdAt: 提醒触发时刻 }
{ type: reminder, copyKey: reminderPermissionBlocked, payload: 设置页,
  createdAt: 发现权限缺失时刻 }
```

**入口策略**：设置页开关仍是唯一编辑入口（不搬家）；消息流里提醒类条目是**只读回执**，点击 payload 跳对应页面（去运动 / 去开权限）。

**利**
- 复用度最高：`ReminderService`、设置页、通知权限链路全是现成，工程量最小。
- 「权限被拒提醒发不出」这条回执有真实的补救价值（当前用户无感知，提醒静默失效）。

**弊**
- 日常信息价值低：每日提醒千篇一律，历史列表刷屏后用户很快疲劳。
- 触达感知有硬伤：进程被杀时通知由系统发出，App 端拿不到可靠「已送达」事件，历史只能是「已调度/推断触发」，与真实触达有偏差，需要文案措辞兜住（「该提醒你啦」而非「已送达」）。

## 3. 形态二：打卡里程碑通知

**定义**：打卡成功使 `streakDays` 恰好命中里程碑档（与 D3-2 徽标同口径：3/7/14/30；100/365 由文案池承接）时，本地生成一条成就消息，可同时补发一条系统本地通知（App 在后台时也有触达）。

**信息结构实例**
```
{ type: milestone, copyKey: streakMilestones[7], copyParams: {},
  payload: 打卡日历页, createdAt: 打卡成功时刻 }
```

**入口策略**：事件驱动插入消息流顶部 + Tab 红点；点击进日历页——那里有 PageHero 连胜专属副标题与 D3-2 徽标，**庆祝的「回礼」在目的地等它**，形成闭环。

**利**
- 口径与文案零新增：`BrandCopy.streakMilestones` 就是消息文案，与首页徽标、日历副标题三位一体，不会出现三处口径打架。
- 情绪价值真实：成就回访是用户愿意点开的消息类型；与 D3「克制的愉悦感」同源。
- 架构上为二期铺路：`type` 字段、红点、消息流容器全部就绪，好友互动/推送届时只是新增一种 type。
- 生成时机可靠：打卡链路里 `user.streakDays` 更新即比对命中，Mock/Live 行为一致，纯前端闭环。

**弊**
- `streakDays` 由服务端计算下发（SPEC 明文），跨设备场景下本地生成时机依赖打卡动作发生在本机——但成就回访本就只对「刚打卡的你」有意义，语义上反而正确。
- 里程碑低频（3 天一条起），单独撑不起一个 Tab 的日常活跃——需要形态一或二期社交内容补量。

## 4. 对比与推荐

| 维度 | 形态一 提醒历史 | 形态二 里程碑通知 |
|---|---|---|
| 工程量 | 小（复用提醒链路） | 小-中（打卡链路挂钩 + 消息流容器） |
| 日常信息价值 | 低（重复性高） | 高（低频但每次都值得点） |
| 数据可信度 | 触达只能推断 | 事件驱动，可靠 |
| 契约/红线影响 | 无 | 无（纯本地，不碰服务端口径） |
| 二期扩展性 | 平 | **好（统一消息模型的最佳首块砖）** |

**推荐：形态二先行，形态一降级为后续并入的一种 `type`。**

分期建议：
1. **第一步（本提案核心）**：统一 `LocalMessage` 模型 + 消息流容器（替换 `_MessagePage` 空态，列表为空时仍回落现有 EmptyState，零浪费）+ 里程碑挂钩生成 + Tab 红点。
2. **第二步**：提醒类回执并入（权限被拒条目优先做——它是当前真实的无声故障点）；消息流顶部保留「提醒设置」快捷入口（跳设置页）。
3. **二期**：`type` 扩 `friend/push`，远程消息与本地消息同流渲染。

**明确不做**：不因消息流引入任何后端接口；不动打卡判定/幂等键；不为红点做轮询后台任务（全部事件驱动）；文案不落字面量进存储（存 `copyKey`，渲染时经 BrandCopy）。

---

## 5. 一句话结论

**用「打卡里程碑通知」给消息 Tab 一个值得点开的开始**：口径与文案直接复用 BrandCopy 里程碑池（与 D3-2 徽标同源），统一 `LocalMessage` 模型天然为二期推送/好友互动留好插槽；提醒历史价值有限且有触达感知硬伤，降级为后续并入的一种消息类型。
